# Contributing

[`LICENSE.md`](LICENSE.md). Dependencies retain their own license terms.

## Start with the problem

Search existing issues and documentation before opening a new proposal. For a
new API, module, protocol, target profile, catalogue entry, or a change that
crosses UETD and uef-gen, open an issue first and describe the problem and the
intended boundary. This is especially important for public C APIs, serialized
formats, generated-project layouts, and safety-related behavior. Small fixes
with an obvious scope can go directly to a pull request.

Use the issue forms for bugs, feature proposals, and catalogue proposals. Keep
one logical change per pull request. Changes that need coordinated edits in
both subprojects should be submitted together so the integration remains
reviewable.

## Contribution expectations

- State what behavior changes and why. Include the affected project (`UETD`,
  `uef-gen`, or both), compatibility implications, and any assumptions.
- Keep the documentation, manifests, schemas, examples, and generated paths in
  sync with code changes. UETD owns embedded APIs and catalogue facts;
  uef-gen consumes those contracts rather than maintaining a parallel copy.
- Keep hardware claims tied to exact evidence. Identify the chip, package,
  board/revision, toolchain, and source documents where applicable. A family
  roadmap entry is not a verified board profile.
- Do not promote scaffolds or fail-closed operations as implemented behavior.
  Preserve explicit unsupported/error behavior until a feature is complete.
- For embedded changes, explain memory use, timing/blocking behavior,
  concurrency assumptions, error handling, and relevant safe-state behavior.
- For numerical or control changes, state conventions, units, dimensions,
  bounds, and the cases used to check correctness.
- Do not include credentials, private keys, customer data, copyrighted vendor
  documents, or binary artifacts without an approved reason and redistribution
  rights. Link to public datasheets/reference manuals instead of copying them.

## Human-led work and AI assistance

AI coding and writing tools are allowed as assistants. The contributor must be
the responsible author: personally review every submitted change, understand
the resulting design, verify factual and licensing claims, and be able to
explain the implementation and its limitations during review. Disclose material
AI assistance in the pull request, naming the tool and describing what it
produced or changed.

Do not submit work that was substantially designed and generated by Claude,
Codex, or another agent when you have not independently reviewed, validated,
and taken responsibility for it. A contributor who cannot explain or defend
the submitted change should expect the pull request to be returned or closed.
This applies equally to human-written and AI-assisted work: the contributor is
accountable for correctness, security, provenance, and maintainability.

## Local validation

Run checks appropriate to the files changed and report the exact commands and
results. Do not claim hardware validation from a host build.

For UETD, a host configure and build can be run from the repository root:

```powershell
cmake -S UETD -B UETD/build -DUETD_TARGET=HOST -DUETD_UOS_BACKEND=BAREMETAL
cmake --build UETD/build
```

For uef-gen, install the package in editable mode from its directory and run
the relevant CLI/schema checks for the change:

```powershell
Set-Location uef-gen
python -m pip install -e ".[templates]"
uef-gen --help
```

At the time this guide was drafted, I did not find a maintained automated test
suite in either subproject. Recheck for the current harness, run the relevant
checks, and include a reproducible validation procedure identifying what could
not be checked. Add focused regression coverage when an appropriate test
harness exists; do not invent or claim a test result.

## Pull requests

Open a pull request from a topic branch against the repository's default
branch. Complete the pull request template, link the issue when there is one,
and keep the diff focused. The maintainer may ask for changes, defer a proposal,
or close it if its scope does not fit the project or cannot be verified.

By submitting a pull request, you confirm that you have the right to submit
the work and agree to the contribution terms published in the repository at
the time the pull request is accepted. The maintainer will publish the chosen
contribution terms and any required sign-off or contributor agreement process
before accepting external code contributions. The project license does not by
itself establish ownership of or permission to license a contribution.
